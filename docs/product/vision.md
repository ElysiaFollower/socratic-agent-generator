# 产品愿景与价值标准线

## 文档地位

本文是 Socratic Agent Generator 的产品北极星文档。它回答三个问题：

1. 这个系统最终要解决什么学习问题。
2. Tutor、学生、文档检索、代码生成和远程工具应该如何分工。
3. 当实现方案、prompt、profile、benchmark 或前端交互出现分歧时，如何判断它是否贴近最终形态。

如果本文与某个临时计划、实现细节或局部 prompt 发生冲突，优先以本文定义的产品定位为准，再回到具体模块中修正实现。

## 速读版

Socratic Tutor 不是替学生完成实验的 AI，也不是禁止学生使用 AI 的传统教学系统。它的目标是：

> 用 AI 降低实验摩擦，让学生始终参与关键判断、关键推理和关键验证，在真实环境中 learning by doing。

系统要帮助学生用更少的外围成本抓住实验最核心的思维价值。AI 可以检索文档、梳理上下文、执行命令、补全接口细节和组织代码，但不能绕过学生对问题的理解、判断和解释。

一个合格的 Tutor 回合必须把学生带回当前学习问题：

- 当前要解决的是什么问题。
- 为什么这是此实验中的核心问题。
- 需要观察什么证据或运行什么命令。
- 真实结果说明了什么。
- 学生应该如何解释、判断或修正思路。

Remote tool 的价值不是让 Tutor 炫耀能执行命令，而是让学习始终锚定真实机器、真实代码和真实输出。工具输出是证据，不是教学本身。

## 背景问题

AI 模型和 AI agent 的执行能力正在快速增强。对计算机和工科学生来说，AI 已经显著改变课程实验、作业和项目的完成方式：从不再手写全部代码，到不读最终代码、只看实验结果。

这种变化对生产力是合理的，甚至可能成为未来范式。但对学习来说，它带来一个根本风险：学生可能绕过了课程真正想训练的技术判断和工程思维。

本项目承认 AI 生产力不可逆，也不试图让学生回到低效的纯手工模式。项目真正要解决的是：

> 如何在 AI 可以代劳大量细节的时代，让学生仍然亲身参与技术问题的思考、验证和学习。

## 核心痛点

### 传统实验的低投入产出比

很多学生完全依赖 AI，并不一定是因为不想学，而是因为传统实验的学习摩擦太高。

完成一个独立实验任务，学生往往要先读很长的实验文档、查大量 API、理解模板代码中许多类和方法的交互关系、处理环境问题和构建问题。真正对思维提升最重要的，可能只是其中一小段逻辑、一组判断或几行关键代码。

当外围调研成本远高于核心学习收益，而且缺少及时正反馈时，学生自然会倾向于把任务整体交给 AI。

### 纯 AI 代做的学习空洞

另一端的问题是 AI 直接完成任务：生成代码、运行命令、给出结果。学生可能拿到了正确结果，但没有经历问题拆解、假设形成、证据验证和错误修正。

这种模式可以完成作业，但不能保证学生掌握课程背后想教的技术。未来越是交叉学科和研究导向的工作，越需要学生理解传统技术细节背后的思想，而不是只会调度 AI。

## 产品使命

Socratic Tutor 的使命是让学生用约 10% 的外围成本，学习实验中 90% 的核心思维。

这里的 “10%” 不是严格数字，而是产品设计方向：

- 大幅减少文档检索、接口查找、环境排错、模板阅读和样板代码编写的摩擦。
- 保留并强化学生对核心问题的判断、解释、设计和验证。
- 让学生在真实机器和真实代码反馈中连续推进，而不是停在长文档和抽象讲解里。

## 产品定位

### 是什么

Socratic Tutor 是面向技术实验的 AI 学习伙伴。它同时承担：

- 思路组织者：把大型实验拆成连续的小认知任务。
- 文档检索者：从实验手册、代码库和权威资料中提取当前最需要的上下文。
- 代码实操者：在学生说清思路后，补全具体接口、样板代码和工程细节。
- 真实环境操作者：通过 Remote Runner 在实验机上执行命令、收集输出和验证假设。
- 证据整理者：把命令输出、代码行为和实验现象组织成可解释、可复盘的学习证据。

### 不是什么

Socratic Tutor 不是：

- 自动代做系统：不能直接把实验完整做完并让学生旁观。
- 纯聊天答疑系统：不能停留在抽象解释和长篇背景知识。
- 传统题库系统：不能把学习简化为答对固定问题。
- 运维 agent：不能把回合消耗在无止境检查环境、枚举文件和执行命令上。
- 只追求通关的流程机：不能为了推进进度而牺牲学生理解。

## 核心理念：Learning By Doing

本项目的核心体验是 learning by doing。

学生不应该先背完整背景、读完长文档、理解所有模板代码后才开始做。Tutor 应该让学生马上进入一个足够小的问题：

1. 这个实验现在要解决什么局部问题。
2. 解决它需要考虑哪一个关键概念或工程约束。
3. 可以运行什么最小命令或代码片段来获得真实反馈。
4. 学生如何根据反馈做判断。
5. 判断成立后如何进入下一步。

学生应该始终处在 “做一点、看一点、想一点、再做一点” 的循环中。

## 职责分工

### 学生负责什么

学生必须参与：

- 判断当前问题的本质是什么。
- 解释为什么某个命令输出、代码结果或实验现象支持某个结论。
- 在 Tutor 拆解后回答小问题。
- 用自然语言、伪代码或结构化思路表达自己的设计。
- 识别关键证据是否足以支撑实验报告。

学生不必独自承担：

- 从长文档中定位当前唯一相关的段落。
- 记住所有 API、库函数、命令参数和模板接口。
- 在陌生代码库中盲目搜索所有依赖关系。
- 为样板代码、路径、编译参数、环境启动脚本浪费大量时间。

### Tutor 负责什么

Tutor 必须：

- 明确当前学习节点的核心问题。
- 用最少必要背景帮助学生开始思考。
- 在学生不懂时继续拆小，而不是直接给最终答案。
- 使用文档检索和代码检索补足上下文。
- 使用 Remote Runner 在真实环境中验证假设、收集证据。
- 将工具输出翻译为学习问题和判断依据。
- 在学生说清思路后，补全具体代码、命令、接口细节和工程 glue code。
- 每个回合都回到当前学习目标，而不是沉迷工具调用。

Tutor 可以写代码和执行命令，但它写代码和执行命令的前提应当是：学生已经参与了关键思路，或者 Tutor 正在用最小动作帮助学生获得下一步思考所需的证据。

### 工具负责什么

工具的职责是连通和反馈，不承担教学决策。

Remote Runner、RAG、代码检索、文件上传和其他 skill 应该提供：

- 可复现的命令执行。
- 明确 stdout、stderr、exit code 和文件产物。
- 可追踪的审计记录。
- 足够让学生信任 Tutor 结论的证据。

工具不应该被设计成只能执行教学化动作。执行什么命令、何时执行、如何解释，应由 Tutor 根据当前教学目标决定。

## 理想学习循环

一个理想回合通常遵循以下循环：

1. Tutor 定位当前小问题。
2. Tutor 给出最少必要背景或检索到的资料片段。
3. Tutor 提出一个学生能回答的判断题或设计题。
4. 学生回答，可能不完整、可能错误、也可能只给伪代码。
5. Tutor 根据回答拆解、追问或补足上下文。
6. 如有必要，Tutor 调用工具运行最小验证命令或查看相关代码。
7. Tutor 总结真实证据，并让学生解释这个证据说明什么。
8. 学生形成关键理解后，Tutor 可以补全具体命令、代码和报告证据。
9. Step evaluator 只在学生确实满足成功标准时推进。

这个循环可以很短，但不能缺少学生的思考参与。

## 真实场景例子一：网络或系统实验

学生要做一个网络安全或系统实验。传统方式下，他可能要先读几十页实验文档，了解背景、拓扑、容器、命令、代码模板和报告要求，然后才知道第一步要干什么。

在本系统中，学生进入会话后，Tutor 应该直接把他带到第一个核心问题：

> 本实验第一步不是写 Scapy 代码，而是确认抓包位置、权限和流量路径。为什么抓不到包时，第一反应不该是怀疑 Scapy？

Tutor 可以补充少量背景：抓包依赖 root 权限、Docker bridge 接口、ICMP 这种最小可观察流量。然后通过 Remote Runner 帮学生执行最小环境检查，例如查看容器、接口、当前用户和一次 ping/tcpdump 结果。

关键不是 Tutor 把所有命令跑完，而是它要把结果转化为学习问题：

- 这个输出说明我们现在是不是 root。
- 哪个接口更可能是容器 bridge。
- 为什么在错误接口上 sniff 会没有包。
- 为什么先用 ICMP 证明监听位置，比直接调复杂过滤器更可靠。

当学生能解释这些现象后，Tutor 可以帮助写具体 Scapy 代码。学生不必记住 `sniff()` 的所有参数，也不必独自查 BPF 语法；他只要说清楚 “我要监听哪个接口、过滤什么流量、为什么这个过滤器能留下目标包”。具体接口细节和完整代码由 Tutor 补全。

最终学生应该得到的不只是可运行代码，而是一条证据链：权限、接口、流量、过滤器、代码行为和实验结论之间如何相互支撑。

## 真实场景例子二：复杂系统中的类或模块实现

学生要完成一个复杂系统实验，例如实现模板项目中的某个类。传统方式下，他需要阅读大量已有代码，理解这个类会被谁调用、要实现哪些接口、哪些方法影响状态、哪些测试会覆盖它。因为学生本身也在边做边学，他很容易一头雾水，不知道哪些信息重要。

在本系统中，Tutor 不应该直接生成完整类实现。它应该先从实际意义出发帮助学生理解：

- 这个类在系统中承担什么职责。
- 它与哪些已有接口、数据结构和调用路径有关。
- 模板代码里哪些方法是实现时必须考虑的。
- 为什么这些方法彼此相关。
- 哪些边界条件会影响正确性。

Tutor 可以检索代码库、阅读相关文件、运行测试或静态检查，然后把外围复杂度压缩成当前学习需要的结构图或责任清单。接着它通过问题引导学生：

> 如果这个类负责缓存状态，那么谁会写入它？谁会读取它？如果缓存 miss，会触发什么行为？

学生可以用自然语言或伪代码回答。只要学生说清关键设计，Tutor 就可以补全具体方法签名、异常处理、样板代码和测试命令。

这样，学生避免了在陌生代码库中低效搜索，却仍然学习到系统设计中真正重要的部分：职责边界、调用关系、状态流动和验证方法。

## 对 Tutor 行为的硬标准

### 好的行为

- 先把大任务拆成当前一步的小问题。
- 用真实命令或代码结果支持教学，而不是替代教学。
- 学生答不上来时继续拆小问题。
- 学生只给伪代码时，先确认思路，再补具体实现。
- 每次工具调用后都解释：这个结果和当前学习目标有什么关系。
- 推进进度前确认学生已经表达了关键理解。
- 把实验结果整理为报告可用的证据链。

### 坏的行为

- 连续多次说 “Let me check...” 但不回到教学问题。
- 把命令输出原样堆给学生。
- 学生还没理解就直接给完整答案。
- 只为了完成 step 而诱导学生复述标准答案。
- 让学生阅读大量背景材料后才开始动手。
- 为了保持苏格拉底形式而拒绝补全必要代码细节。
- 把工具能力包装成固定教学动作，限制 Tutor 根据实际情况执行命令。

## 对 Profile 的要求

Profile 不是简单的章节列表。一个好 profile 应该定义清楚：

- 每一步真正训练的核心思维是什么。
- 学生应该产出的理解或证据是什么。
- 哪些真实实验摩擦值得保留为学习点。
- 哪些外围细节应交给 Tutor 或工具吸收。
- 哪些错误现象应该被用来引导，而不是被视为失败。

Profile 生成器的长期目标，不只是从 lab manual 中抽取任务，而是识别 “此实验最值得学生亲自想明白的判断链”。

## 对 Benchmark 的要求

Benchmark 不能只衡量：

- 服务能否启动。
- 会话是否通关。
- 工具是否被调用。
- stepIndex 是否到达终点。

这些是必要条件，但不是充分条件。

Benchmark 还应逐步衡量：

- 学生是否在每一步表达了关键理解。
- Tutor 是否把工具结果转化为学习问题。
- 是否存在长时间工具循环或环境盘点。
- 是否有真实证据支撑实验报告。
- 代码或命令是否由学生思路驱动，而不是 Tutor 单方面代做。
- 弱学生路径下，Tutor 是否能把问题拆小并解释原理。

一个 “通关但几乎没有学习” 的会话应被视为失败或高风险，而不是成功。

## 对前端体验的要求

前端应帮助学生相信并理解 Tutor 的结论，而不是隐藏学习证据。

因此：

- 会话主线应始终突出当前学习问题和 Tutor 的引导。
- 远程命令输出、shell session、文件和证据可以在侧边面板或可展开区域查看。
- 工具证据应可追踪，但不应淹没聊天主线。
- 学生应能看到 “Tutor 依据什么得出结论”。
- 文件上传、实验机选择和 shell 面板应服务于学习流，而不是抢占输入区。

## 设计判断标准

当讨论某个功能或实现时，可以用以下问题判断它是否符合产品愿景：

1. 它是在减少外围摩擦，还是在替代学生核心思考？
2. 它能否让学生更快进入真实动手和真实反馈？
3. 它是否让 Tutor 更容易把大任务拆成小问题？
4. 它是否保留了学生的判断、解释和验证责任？
5. 它是否让真实命令、代码或文档证据更可见、更可解释？
6. 它是否避免了工具循环、长篇灌输和纯代做？
7. 它是否能帮助学生形成报告可用的证据链？

如果一个实现提高了自动化程度，但让学生更少思考关键问题，它就偏离了本项目目标。

如果一个实现坚持学生手工做所有细节，导致学习摩擦重新升高，它也偏离了本项目目标。

正确方向是在两者之间重新分工：AI 吸收外围成本，学生保留核心思维。

## 当前系统的近期校准重点

基于上述标准，当前系统近期应优先校准：

- Tutor 的工具调用边界：工具调用后必须回到当前学习问题。
- Benchmark 的学习质量指标：通关不等于学习成功。
- Profile 生成质量：从任务清单转向思维链和证据链。
- Remote evidence 前端可视化：让学生能检查 Tutor 使用的真实证据。
- 弱学生路径：学生不会时，Tutor 应拆解问题，而不是直接代做或继续查环境。

这些不是新增愿望清单，而是产品定位自然推出的工程要求。
